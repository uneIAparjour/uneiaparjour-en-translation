  • Bonus : WordPress 7.0.4 (balise generator) et Yoast SEO gratuit 28.2 (pas de Premium installé, les routes IA vues plus tôt sont désormais dans le forfait gratuit de Yoast)

Confirme que Yoast n'enregistre pas _yoast_wpseo_title/_yoast_wpseo_metadesc comme meta REST standard — le plugin custom (étape 02) devra les exposer lui-même via register_rest_field(), pas de route Yoast native pour ça

  • Utilisateur translation-bot créé, rôle Auteur/autrice — ne pourra jamais toucher aux 1300 articles FR existants ni aux réglages du site

02

Plugin pont (Polylang + SEO)

Le seul code qui touche vraiment au cœur de WordPress — à traiter avec le plus de précaution.

  • Plugin classique écrit (translation-bridge.php, jamais un mu-plugin), endpoint POST /translation-bridge/v1/link qui appelle pll_set_post_language() et pll_save_post_translations()
  • Même plugin : 2 champs de suivi exposés via register_post_meta() (_translation_source_hash, _translation_locked) + titre/description Yoast via register_rest_field() (yoast_title, yoast_metadesc) — voir encart, ces deux-là ont dû changer de mécanisme
  • Endpoint protégé par current_user_can('edit_posts') — jamais ouvert sans contrôle
  • Envelopper les paragraphes traduits dans les commentaires de bloc Gutenberg — reporté à l'étape 03, c'est le script de traduction qui construit le contenu à l'écriture, pas ce plugin
  • Testé dans WordPress Playground — namespace et route confirmés, aucune erreur fatale à l'activation (Playground n'avait pas Yoast, d'où le bug découvert seulement en prod)
  • Déployé sur le vrai site, activé sans erreur, les 4 champs et l'endpoint de liaison confirmés fonctionnels en prod après correctif
Bug découvert en prod, corrigé : Yoast SEO enregistre lui-même _yoast_wpseo_title/_yoast_wpseo_metadesc avec show_in_rest => false, et se charge après notre plugin (ordre alphabétique) — sa déclaration écrasait la nôtre. Playground n'avait pas Yoast installé, donc le test initial ne l'a pas repéré. Corrigé en passant ces deux champs spécifiques sur register_rest_field() (contourne le registre global de register_meta), plutôt que de dépendre de l'ordre de chargement des plugins.
Pourquoi un plugin classique : il bénéficie de la protection anti-erreur fatale de WordPress (désactivation auto + email de récupération depuis WP 5.2). Un mu-plugin n'a pas ce filet, et il n'y a pas d'environnement de préprod chez OVH pour l'instant.
03

Script de traduction

Un workflow GitHub Actions planifié gère à la fois le stock initial et la synchro quotidienne — pas de cron-job.org sur ce projet (timeout de 30s incompatible avec la traduction synchrone).

  • Récupération via REST des articles uniquement — lib/wp.js, exclut les IDs EN déjà connus plutôt que de dépendre du filtrage lang de Polylang (non confirmé fiable)
  • Appel Azure Translator, tag_handling=html, glossaire via dynamic dictionary — lib/azure.js, syntaxe <mstrans:dictionary> vérifiée contre la doc officielle
  • Détection de changement par hash SHA-256 du contenu source — lib/state.js
  • Protection contre l'écrasement d'une correction humaine (_translation_locked) — vérifié avant toute mise à jour, skip + log si verrouillé
  • Réécriture des liens internes via table de correspondance de slugs, dégradation propre vers le FR si pas encore traduit — lib/content.js, plus un mode --repair-links pour la passe de rattrapage
  • Catégories/tags FR↔EN créés à la volée et mis en cache — lib/taxonomy.js + config/taxonomy-map.json (limite connue : la langue Polylang des termes créés n'est pas explicitement définie, à surveiller)
  • Médias réutilisés (pas de re-upload) — simple copie de featured_media
  • Statut brouillon uniquement à la création — bug trouvé et corrigé en relecture : la première version forçait "brouillon" à chaque resynchronisation, ce qui aurait annulé la publication d'un article déjà validé par un humain
  • Petits lots (--limit, 15 par défaut), état sauvegardé après chaque article traité (pas seulement en fin de lot)
  • Une erreur sur un article n'interrompt jamais les suivants — captée, loggée dans l'état, le script continue
  • Mode --dry-run implémenté
  • Workflow GitHub Actions écrit — .github/workflows/translate.yml, planifié quotidien + déclenchement manuel, committe l'état mis à jour après chaque run

06

Bascule en automatique

Une fois le panel validé, le reste du stock (∼1250 fiches restantes) suit progressivement, avec un palier intermédiaire avant la vitesse de croisière.

  • Palier intermédiaire : étendre à ~150 fiches (toujours brouillon) avant de passer en publication directe — le panel de 50 ne couvre pas forcément tous les cas particuliers des 1300
  • Démarrage prudent de l'indexation : ~20–30 fiches/jour la première semaine, en surveillant Search Console, avant d'accélérer
  • Rythme de croisière 100 à 200 fiches/jour au maximum — jamais les 1300 d'un coup, pour éviter un pic d'indexation SEO artificiel
  • Activer le sélecteur de langue Polylang dans le menu une fois assez de contenu EN publié
07

Flux quotidien continu

Le régime de croisière, une fois le stock écoulé.

  • Workflow GitHub Actions planifié : détecte les FR nouveaux ou modifiés sans EN à jour
  • Traduction Azure, création en brouillon (tant que la confiance n'est pas totale), puis publication directe
  • Volume attendu : ~20–25k caractères/mois, très loin sous le quota gratuit Azure (2M/mois)
